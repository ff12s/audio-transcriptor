# Запись созвона из приложения + разметка «Я / Собеседники»

Дата: 2026-10-20. Статус: черновик на утверждение.

## Зачем

Сейчас `transcribe` работает только с готовым файлом. Пользователь созванивается в Chrome
(Meet и т.п.) или в отдельном приложении (Zoom, Teams, Telegram) и хочет в конце получить `.md`
как сейчас, без отдельной программы записи. Параллельно может играть музыка или звук
других приложений, и в запись он попадать не должен.

## Цели

- Новая команда `record`: пишет звук **одного приложения** (дерево его процессов) и
  **микрофон** пользователя в две отдельные дорожки, пока пользователь не нажмёт Ctrl+C.
- Сразу после остановки обе дорожки транскрибируются тем же Whisper-конвейером, и рядом
  сохраняется `.md`, в котором реплики помечены `Я` (микрофон) и `Собеседники` (приложение).
- Флаги `--title/--date/--participants/--model/--overwrite`, глоссарий, переменные
  `MEETING_NOTES_*` и формат frontmatter работают как у `transcribe`.

## Не цели

- Захват отдельной вкладки Chrome (нужно расширение; отложено пользователем).
- Транскрипция в реальном времени.
- Различение собеседников между собой (диаризация).
- Подавление эха без наушников: если микрофон слышит динамики, реплики собеседников
  продублируются в `Я`. В README пишем: используйте наушники.
- Компенсация дрейфа часов между микрофоном и приложением (на часовой встрече это секунды,
  для разметки реплик некритично).
- Linux/macOS.

## Анти-цели (провал, даже если «работает»)

- Запись потеряна: упал Whisper, не хватило VRAM, ошибка записи `.md`, и звук пропал.
  Дорожки пишутся на диск **по ходу записи**, а не копятся в памяти, и остаются на диске
  в любом исходе.
- В запись попадает звук других приложений (системный loopback вместо per-process).
- Изменилось поведение существующей команды `transcribe` или формат её `.md`.

## Ограничения

- Windows build 20348+ (требование API Process Loopback). На практике это Windows 11 или
  Server 2022: ни один выпуск Windows 10 до этой сборки не дошёл (22H2 — это 19045). В README
  писать «Windows 11». Перед записью проверять сборку и при несоответствии выдавать понятную ошибку.
- Python 3.12, uv, существующие зависимости (`faster-whisper 1.2.1`, `av 18.1.0`,
  `numpy 2.5.4`, `typer 0.27.3`).
- Новые зависимости (решение принято при согласовании): `proc-tap` (захват процесса),
  `soundcard` (микрофон), `psutil` (поиск процесса по имени и корня его дерева). Только под
  `sys_platform == 'win32'`, кроме случаев, когда пакет нужен для импорта на всех платформах.
  Добавлять что-либо ещё нельзя без согласования.

## Как это выглядит для пользователя

```powershell
uv run record --app chrome "D:\records\standup" --title "Стендап" --participants "Анна, Борис"
# ... созвон ...  Ctrl+C
```

На диске:

```
D:\records\standup.me.wav     # микрофон
D:\records\standup.them.wav   # приложение
D:\records\standup.md         # транскрипт
```

Фрагмент `.md` (frontmatter как сейчас):

```
[01:12] **Я:** Давайте начнём со статуса по релизу.

[01:20] **Собеседники:** Релиз готов, ждём QA.
```

- `--app` обязателен: имя исполняемого файла без учёта регистра, `.exe` можно не писать
  (`chrome`, `Zoom`, `ms-teams`). Если такого процесса нет, ошибка с понятным текстом
  **до** начала записи.
- Во время записи в консоли видно, что идёт запись, и прошедшее время. Индикатор уровня по
  дорожкам желателен, но не обязателен.
- Если `.md` уже есть и нет `--overwrite`, ошибка **до** начала записи, как у `transcribe`.
  Если уже есть `.wav` с тем же именем, тоже ошибка до записи (их `--overwrite` не трогает
  и не перезаписывает).
- Если транскрипция после записи упала, сообщение говорит, где лежат дорожки и какой
  командой их перетранскрибировать без повторной записи.

## Проверенные факты (grounding, 2026-10-20)

- **Process Loopback (Microsoft).** `ActivateAudioInterfaceAsync` с
  `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK` захватывает звук, который рендерит процесс
  **и его дочерние процессы**. Режим `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE` /
  `EXCLUDE`. Нужен Windows 10 build 20348+. Если процесс ничего не играет, приходит тишина.
  Источники: [пример Microsoft](https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/),
  [PROCESS_LOOPBACK_MODE](https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ne-audioclientactivationparams-process_loopback_mode).
- **Chrome.** Звук играет не корневой `chrome.exe`, а дочерний процесс аудиосервиса.
  Поэтому цель захвата — **корень дерева** (процесс приложения, у которого родитель не
  процесс с тем же именем), режим include-tree. *Это вывод, а не проверенный факт:
  подтверждается шагом 1 плана.*
- **proc-tap 1.1.1** (PyPI, 2026-07-22, MIT, wheel `cp312-win_amd64`, зависимости numpy+scipy).
  API: `ProcTap(pid, StreamConfig(), on_data=cb)`, `start()`, `stop()`/`close()`. Колбэк
  получает `(pcm: bytes, frames: int)`. Также есть `read(timeout=...)`. Формат на Windows:
  48 kHz, 2 канала, float32 (при сбое инициализации fallback 44.1k int16 → 48k float32).
  **Поправка после шага 1:** реальный API 1.1.1 — `ProcessAudioCapture(pid, on_data=cb)`, колбэк `(bytes, -1)`; режим INCLUDE_TARGET_PROCESS_TREE подтверждён в исходнике и на живом созвоне (см. план, «Результат Task 0").
  Пример записи WAV в README ошибочен (44.1k, int16 для float32-данных), его не копировать.
  Проект маленький (19★). Если шаг 1 провалится, запасной вариант — своя тонкая обёртка над
  тем же API через `comtypes` по образцу примера Microsoft; это новое решение, его надо
  согласовать с пользователем.
  Источники: <https://pypi.org/project/proc-tap/>, <https://github.com/m96-chan/ProcTap>.
- **soundcard 0.4.6** (context7 `/bastibe/soundcard`): `sc.default_microphone().recorder(
  samplerate, channels=None, blocksize=None)` — context manager. `rec.record(numframes)`
  возвращает `float32` массив `(frames, channels)`.
  Подводные камни: **на WASAPI запись одного канала даёт мусор**, поэтому пишем все каналы
  (или `[0, 1]`) и сводим в моно сами. Blocksize на WASAPI может игнорироваться. При
  недогрузке брать blocksize больше numframes. При разрыве данных идёт
  `SoundcardRuntimeWarning("data discontinuity in recording")`. COM инициализируется в MTA,
  а `RPC_E_CHANGED_MODE` библиотека не считает ошибкой.
- **faster-whisper 1.2.1** (context7 `/systran/faster-whisper`): `transcribe(audio)` принимает
  путь, file-like или float32 ndarray. Возвращает **ленивый генератор** сегментов и `info`
  (`duration`). `vad_filter=True` вырезает тишину. Существующий `WhisperTranscriber`
  принимает путь, его можно переиспользовать для каждой дорожки как есть.

## Решения по «как» (согласованы с пользователем)

- Источник: одно приложение по имени процесса, не системный звук и не вкладка.
- Две раздельные дорожки, разметка `Я` / `Собеседники`.

## Решения, принятые мной (пользователь может оспорить)

- Имена файлов: `<база>.me.wav`, `<база>.them.wav`, `<база>.md`. Аргумент команды — путь
  без расширения.
- Дорожки на диске: WAV, моно, **16 kHz, int16** (то, что Whisper всё равно использует).
  48k→16k ровно 3:1, `scipy.signal.resample_poly` (scipy уже приходит с proc-tap). Около
  115 МБ на час на дорожку. Запись в файл **инкрементальная** (stdlib `wave`), чтобы сбой
  посреди записи не терял уже записанное.
- Обе дорожки стартуют одновременно, их время отсчитывается от общего старта. Метки
  времени сегментов берутся из Whisper как есть.
- Слияние: сегменты обеих дорожек сортируются по `start`. Склейка в абзацы
  (`merge_segments`) идёт **только внутри непрерывной серии одного говорящего**: смена
  говорящего всегда начинает новый абзац. Метка: `[mm:ss] **Я:** текст`.
- Модель Whisper загружается **один раз** на обе дорожки.
- `source` во frontmatter: имя базы (`standup`). `duration` равна длительности более
  длинной дорожки.
- `transcribe` (существующая команда) не меняется.
- **Несколько деревьев под одним `--app`** (два профиля Chrome и т.п.): захватываются все
  корни, их звук суммируется в `.them.wav`. Новых флагов (`--pid`) нет.
- **Если include-tree в proc-tap не работает** (шаг 1 показал тишину на корне), разрешённый
  fallback без согласования: отдельный `ProcTap` на каждый процесс дерева с суммированием в
  одну дорожку. Звук при этом всё так же только от этого приложения. Не заработало и это —
  стоп и согласование comtypes-обёртки.
- **Тишина приложения.** Дорожка `.them.wav` обязана идти по настенным часам: если loopback
  не присылает пакетов, пока приложение молчит, разрыв заполняется нулями по прошедшему
  времени. Иначе реплики «Собеседников» съедут относительно «Я». Это корректность, а не
  компенсация дрейфа. То же для микрофона (soundcard синтезирует нули сам, но проверить).
- **Приложение закрылось во время записи**: запись продолжается до Ctrl+C (дорожка
  приложения пишет тишину), в консоль выводится предупреждение. Переподключения к новому
  процессу нет.
- **Зависимости.** `scipy` добавляется прямой зависимостью (win32-only), а не только
  транзитивно через proc-tap. `types-psutil` идёт в dev-группу. Для `soundcard`/`proctap`
  нужно `ignore_missing_imports` в mypy, как сделано для `faster_whisper`.

## Что оставлено исполнителю

- Структура модулей (например `capture.py` для записи, расширение `models.Segment` полем
  говорящего или отдельная модель) — в стиле репо, минимально.
- Как именно перетранскрибировать пару дорожек без записи (отдельный флаг `record`, новая
  команда или режим `transcribe`). Требование одно: путь существует и указан в сообщении
  об ошибке и в README.
- Поток/потоки для двух захватов и корректная остановка по Ctrl+C. Требование: после
  Ctrl+C обе дорожки корректно закрыты (заголовок WAV валиден) и транскрипция стартует.
- Тесты: всё, что не требует реального звука (выбор корня дерева процессов, слияние и
  разметка, рендер, ошибки до записи, пайплайн с поддельным захватом и транскрайбером).
  Реальный захват проверяется вручную, шаг 1.

## План проверки до основной работы (шаг 1)

Одноразовый скрипт (не в продукт): найти корень `chrome.exe`, 15 секунд писать через proc-tap,
пока в одной вкладке Chrome играет видео, а в другом приложении (например, плеер Windows)
играет музыка. В середине видео ставится на паузу на ~5 секунд. Ожидаем: в WAV есть звук
Chrome и нет звука плеера. Длина WAV равна настенному времени записи (±0.5 с), то есть
пауза не «съедена». Плюс проверка: приходят ли от proc-tap пакеты во время паузы. Не
прошло — fallback из раздела решений, затем стоп и согласование.
